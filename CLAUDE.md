# Five Nines

2D browser game: take client jobs to build servers, homelabs and mini datacenters, configure the whole hardware and software stack, deliver it. The depth is a simulation driven by real hardware specs.

- The design brief is `docs/design-plan.md`. Read it before doing anything.
- Every decision the user has made since the brief is in `docs/decisions.md`. It overrides the brief where they differ.
- Research notes and sources are in `docs/research/`.

## Rules (from the brief, apply to all work)

1. **Never guess.** If something is not in the brief or decisions log and you do not know it, ask the user. Do not invent numbers, specs, formulas, mechanics or features.
2. **Research instead of assuming.** Hardware specs, benchmarks, engine behavior: look it up with web tools, open the page, keep the source.
3. **Stay inside the brief.** Locked decisions are fixed. No simplified mechanics.
4. **Ask once, up front** for each stage's blocking decisions, then build without stopping for trivia.
5. **Label where data comes from.** Every catalog number and sim constant is tagged `published`, `measured` (with a source) or `estimate` (with reasoning). The validator enforces this.
6. **Verify by running.** Tests, calibration script, and the browser. Don't claim a feature works because the code exists.
7. **Report honestly.** What works, what doesn't, what you were unsure about.
8. **Tone:** direct, no filler.

## Project rules added by the user

- **No real product names in the shipped bundle.** Real names (`realRef`, source titles/URLs, manufacturer names, engine/model real names until the user allows them) live only in `data-dev/`. The game imports only `src/generated/game-data.json`, which `scripts/build-game-data.js` writes with provenance stripped and generic source labels. `npm run build` runs `scripts/check-dist-brands.js` and fails on any real name in `dist/`.
- **Tensor parallel is not layer split.** Sequential stages (layer split, CPU offload) add their times. A TP group's time is its slowest shard plus the all-reduce cost.
- **Cloud/VM hosting is a workload,** but its simulation model is not designed until the user answers the checkpoint question. Don't invent one.
- Don't report the example job as generated end to end until the job generator exists (stage 4), or difficulty as working until stage 10.

## Layout

- `data-dev/` dev-only source data with real names and full provenance. Never imported by game code. Written as JS modules using the `pub/meas/est` helpers in `data-dev/lib.js`, so every value is tagged. `data-dev/fitted-perf.js` is generated by `npm run calibrate -- --fit`; don't edit it by hand.
- `scripts/build-game-data.js` writes `src/generated/game-data.json` (gitignored, regenerated by every npm script).
- `src/data/` loader and validator. `src/sim/` the simulation engine, pure functions, no UI.
- `scripts/calibrate.js` prints sim vs published benchmark error.
- `dev/sim-harness.html` dev-only page, served by `vite dev`, never in `dist/`.
- `tests/` Vitest.

## Commands

- `npm test` regenerates game data and runs Vitest.
- `npm run calibrate` prints the calibration table (`-- --fit` refits engine constants on the `role: 'fit'` benchmark cases). `docs/calibration.md` holds the latest table and what the errors mean.
- `npm run build` regenerates data, builds, and runs the brand check.
- `npm run dev` then open `/dev/sim-harness.html`.
